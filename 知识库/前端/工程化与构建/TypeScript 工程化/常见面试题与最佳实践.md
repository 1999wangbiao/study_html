## 一、基础概念类（高频）

### 1. TypeScript 与 JavaScript 的关系？为什么选 TS？

**核心答案**：TS 是 JS 的超集，添加静态类型系统，编译后类型被擦除等价于 JS。

| 维度 | JS | TS |
|---|---|---|
| 类型 | 动态（运行时） | 静态（编译时） |
| 类型信息 | 运行时存在 | 编译后擦除 |
| 学习曲线 | 低 | 中 |
| 工程化 | 弱 | 强（重构、IDE） |

**为什么选 TS**：

- **编译时暴露 bug**：类型错误在编译时发现，运行时少 bug。
- **大型项目重构友好**：改类型让所有引用处报错，不会漏。
- **IDE 智能提示**：类型让补全、跳转、重构更准。
- **API 文档化**：类型即文档，读接口签名就懂用法。
- **团队协作**：类型约束让代码意图清晰。

**关键认知**：

- 合法 JS 都是合法 TS——TS 不破坏 JS 语义。
- TS 编译后**完全等价于 JS**，运行时无类型信息。
- TS 不引入运行时开销——类型在编译时擦除。

### 2. tsconfig.json 的核心字段有哪些？

**核心答案**：target、module、moduleResolution、lib、jsx、strict、esModuleInterop、skipLibCheck、isolatedModules、paths 等。

```json
{
  "compilerOptions": {
    "target": "ES2022",           // 输出语法版本
    "module": "ESNext",           // 输出模块格式
    "moduleResolution": "Bundler",// 模块解析策略
    "lib": ["ES2022", "DOM"],     // 可用全局类型
    "jsx": "react-jsx",           // JSX 处理
    "strict": true,               // 严格模式
    "esModuleInterop": true,      // CJS/ESM 互操作
    "skipLibCheck": true,         // 跳过 .d.ts 检查
    "isolatedModules": true,     // 独立编译（esbuild）
    "noEmit": true,               // 只检查不输出
    "paths": { "@/*": ["src/*"] } // 路径别名
  }
}
```

**关键字段**：

- **target**：输出 JS 语法版本（ES5/ES2022/ESNext）。只降级语法不补 polyfill。
- **module**：输出模块格式（CommonJS/ESNext/NodeNext）。
- **moduleResolution**：解析策略（node/node16/bundler）。
- **lib**：全局类型声明（ES2022/DOM/@types/node）。
- **jsx**：JSX 处理（react/react-jsx/preserve）。
- **strict**：开启所有严格检查（推荐 true）。
- **esModuleInterop**：CJS 默认导入兼容。
- **skipLibCheck**：跳过 .d.ts 检查加速。
- **isolatedModules**：esbuild/SWC 项目必开。
- **noEmit**：只检查不输出（配合 Vite/Webpack）。

### 3. strict 模式都开了什么？

**核心答案**：strict 是 8 个严格检查的组合开关。

| 子选项 | 作用 |
|---|---|
| `strictNullChecks` | null/undefined 必须显式处理 |
| `strictFunctionTypes` | 函数参数逆变检查 |
| `strictBindCallApply` | bind/call/apply 类型安全 |
| `strictPropertyInitialization` | 类属性必须初始化 |
| `noImplicitAny` | 禁止隐式 any |
| `noImplicitThis` | this 隐式 any 禁止 |
| `alwaysStrict` | 输出 "use strict" |
| `useUnknownInCatchVariables` | catch 变量为 unknown |

**strictNullChecks 示例**：

```ts
// 不开：null 可以赋给任何类型
const x: string = null;  // 不报错

// 开：必须显式处理
const x: string | null = null;  // 显式 union
const y: string = null!;         // 非空断言
```

**strictFunctionTypes 示例**：

```ts
// 不开：协变（不安全）
let f: (x: Animal) => void;
let g: (x: Dog) => void;
f = g;  // 允许，但运行时可能传非 Dog 报错

// 开：逆变检查（安全）
f = g;  // 报错：Dog 不能赋给 Animal
```

## 二、类型系统类（高频）

### 4. 类型与运行时的差异是什么？

**核心答案**：类型只在编译时存在，编译后被完全擦除——`interface`/`type` 等运行时不存在，只有 `enum` 和少数构造会保留。

```ts
// TS 源码
interface User { name: string; age: number; }
const u: User = { name: "Tom", age: 18 };

// 编译后
const u = { name: "Tom", age: 18 };
// interface 不存在！
```

**运行时保留的 TS 特性**：

```ts
// enum：保留为对象
enum Color { Red, Green, Blue }
// 编译为：
var Color;
(function (Color) {
  Color[Color["Red"] = 0] = "Red";
})(Color || (Color = {}));

// 参数属性（构造器简写）
class User {
  constructor(public name: string) {}
}
// 编译为：
function User(name) { this.name = name; }
```

**const enum**：编译时内联，运行时不存在。

```ts
const enum Color { Red }
const c = Color.Red;  // 编译为 const c = 0;
```

**关键认知**：

- `instanceof User` 在 interface 下会报错——User 运行时不存在。
- `typeof x === "User"` 不可能——类型不在运行时。
- 类型断言 `as` 只骗编译器，运行时不转换。

```ts
const x = "hello" as unknown as number;
x.toFixed();  // 运行时崩溃
```

### 5. isolatedModules 是什么？为什么 Vite/esbuild 必开？

**核心答案**：`isolatedModules` 假设每个文件被独立编译，禁止依赖跨文件类型信息的特性。esbuild/SWC/Babel 都是这样编译，所以必开。

**禁用的特性**：

```ts
// 1. const enum（独立编译无法内联）
const enum Color { Red }  // 报错

// 2. 不导出 type-only
export { SomeType };  // 报错，必须 export type

// 3. 强制类型导入用 import type
import { type User } from "./types";  // 或 import type
```

**为什么独立编译**：

- esbuild/SWC/Babel 都按文件单独转译，**不做类型检查**，只去掉类型注解 + 降级语法。
- TS 某些特性（如 const enum 内联）需要看到所有使用文件才能编译，独立编译不支持。

**verbatimModuleSyntax（更严格）**：

```json
"verbatimModuleSyntax": true
```

强制所有类型导入用 `import type`，让 esbuild 等能直接擦除而不需判断哪些是类型。

```ts
// 强制
import type { User } from "./types";   // 只导入类型
import { addUser } from "./api";      // 只导入值

// 不能混
import { User, addUser } from "./types";  // 报错
```

### 6. type 与 interface 有什么区别？

**核心答案**：`interface` 描述对象形状、可声明合并；`type` 描述任意类型、不可合并。两者大多数场景可互换。

| 维度 | interface | type |
|---|---|---|
| 描述对象形状 | ✓ | ✓ |
| 描述联合/交叉 | ✗ | ✓ |
| 描述元组/字面量 | ✗ | ✓ |
| 声明合并 | ✓（同名自动合并） | ✗（同名报错） |
| 扩展 | `extends` | `&` 交叉 |
| 性能 | 略好（缓存友好） | 略慢 |

```ts
// interface 声明合并
interface User { name: string; }
interface User { age: number; }
// 合并为 { name: string; age: number }

// type 不能合并
type User = { name: string };
type User = { age: number };  // 报错：重复声明
```

```ts
// type 描述联合
type Status = "active" | "inactive";

// type 描述函数
type Handler<T> = (event: T) => void;

// type 描述条件类型
type IsString<T> = T extends string ? true : false;
```

**选型建议**：

- 对象形状：优先 `interface`（可扩展、可合并）。
- 联合/交叉/条件/函数：用 `type`。
- 库的 API：`interface`（让用户可扩展）。

## 三、tsconfig 配置类（高频）

### 7. target 与 lib 怎么配合？

**核心答案**：`target` 控制语法降级（如 async/await），`lib` 控制可用全局 API 类型（如 Promise、DOM）。两者要协调——target 低时 lib 也要对应版本。

**示例**：

```json
// 兼容老浏览器
{
  "target": "ES5",           // 语法降级到 ES5
  "lib": ["ES5", "DOM"]     // API 类型只到 ES5
}

// 现代浏览器
{
  "target": "ES2022",       // 保留 async/await 等现代语法
  "lib": ["ES2022", "DOM"] // API 类型到 ES2022
}

// Node 项目
{
  "target": "ES2022",
  "lib": ["ES2022"],        // 不需要 DOM
  "types": ["node"]          // 用 @types/node
}
```

**关键**：`target` 只降级语法，**不补 polyfill**。Promise、Array.prototype.flat 等运行时 API 仍需 core-js 或运行时支持。

```ts
// target: "ES5"
async function fn() { return 1; }
// 编译为 generator + helper，但 Promise 仍需运行时支持

// 如果目标环境是 IE11（无 Promise），需补 polyfill：
import "core-js/stable/promise";
```

### 8. module 与 moduleResolution 怎么选？

**核心答案**：根据运行环境选——Vite/Webpack 用 `ESNext + Bundler`；Node 项目用 `NodeNext + NodeNext`。

| 项目类型 | module | moduleResolution |
|---|---|---|
| Vite/Webpack | `ESNext` | `Bundler` |
| Node ESM | `NodeNext` | `NodeNext` |
| Node CJS | `CommonJS` | `Node` |
| 浏览器直跑 | `ESNext` | `Bundler` |

**为什么 Vite 用 Bundler**：

- Bundler 模拟打包器解析，最宽松——允许 `.ts` 扩展名、不强制 `.js` 后缀。
- ESM 严格（必须 `.js` 后缀、严格 `type: "module"`），与 Vite 配置不友好。

**Node ESM 项目**：

```json
// package.json
{ "type": "module" }

// tsconfig.json
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "NodeNext"
  }
}
```

强制 `import "./x.js"`（即使是 `.ts` 源码，import 路径要写 `.js`）——因为 Node ESM 严格按文件名解析。

### 9. paths 与 Vite/Webpack alias 怎么同步？

**核心答案**：tsconfig `paths` 让 IDE 跳转、TS 类型检查；Vite/Webpack `resolve.alias` 让运行时解析。两边必须同步。

```json
// tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}
```

```ts
// vite.config.ts
import path from "node:path";
export default {
  resolve: {
    alias: { "@": path.resolve(__dirname, "src") },
  },
};
```

**为什么必须同步**：

- 只配 tsconfig：IDE 跳转 OK，但运行时 Vite 解析失败 404。
- 只配 Vite：运行时 OK，但 TS 报错"找不到模块"，IDE 无法跳转。

**自动化**：用 `vite-tsconfig-paths` 让 Vite 自动读 tsconfig paths：

```bash
pnpm add -D vite-tsconfig-paths
```

```ts
import tsconfigPaths from "vite-tsconfig-paths";
export default {
  plugins: [tsconfigPaths()],
};
```

## 四、声明文件类（高频）

### 10. .d.ts 是什么？怎么为第三方包加类型？

**核心答案**：`.d.ts` 是类型声明文件，只含类型不含运行时代码。第三方包无类型时用 `declare module` 或 `@types/xxx`。

**全局声明**：

```ts
// globals.d.ts
declare const __APP_VERSION__: string;

declare interface Window {
  api: {
    openFile: () => Promise<string>;
    readFile: (p: string) => Promise<string>;
  };
}
```

```ts
// 业务代码
console.log(__APP_VERSION__);
const path = await window.api.openFile();
```

**模块声明**：

```ts
// types/third-party.d.ts
declare module "third-party-no-types" {
  const x: any;
  export default x;
  export function foo(): void;
}
```

```ts
import x, { foo } from "third-party-no-types";
```

**资源声明**：

```ts
declare module "*.png" { const src: string; export default src; }
declare module "*.svg" { const src: string; export default src; }
declare module "*.css" {
  const content: Record<string, string>;
  export default content;
}
```

**用 @types/xxx**：

```bash
pnpm add -D @types/lodash @types/node @types/react
```

`@types/xxx` 包是 DefinitelyTyped 社区维护的第三方类型声明，自动被 TS 加载（在 `node_modules/@types/`）。

### 11. 怎么为发布的 npm 库生成 .d.ts？

**核心答案**：用 `vite-plugin-dts` 在 build 时自动生成，或在 package.json 配 `types` 字段指向 .d.ts。

**方式 1：vite-plugin-dts**：

```bash
pnpm add -D vite-plugin-dts
```

```ts
// vite.config.ts
import dts from "vite-plugin-dts";
export default {
  plugins: [dts({
    insertTypesEntry: true,    // 生成 index.d.ts 入口
    rollupTypes: true,         // 合并为单文件
    include: ["src"],
    exclude: ["**/*.test.ts"],
  })],
};
```

构建后 `dist/index.d.ts` 自动生成。

**方式 2：tsc 生成**：

```json
// tsconfig.json
{
  "compilerOptions": {
    "declaration": true,        // 生成 .d.ts
    "emitDeclarationOnly": true, // 只生成 .d.ts 不编译 JS
    "outDir": "dist/types",
    "rootDir": "src"
  }
}
```

```bash
tsc
```

**package.json 配置**：

```json
{
  "main": "./dist/index.js",
  "module": "./dist/index.esm.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.esm.js",
      "require": "./dist/index.cjs.js"
    }
  },
  "files": ["dist"]
}
```

**exports.types 必须放第一位**——Node 12+ 解析 exports 时优先匹配第一个。

## 五、构建集成类（高频）

### 12. Vite 怎么集成 TS？dev 与 build 的差异？

**核心答案**：Vite 用 esbuild 转译 TS（不检查类型）；dev 期不跑类型检查、build 期先 `tsc --noEmit` 再打包。

```json
// package.json
{
  "scripts": {
    "dev": "vite",                          // 只转译
    "build": "tsc --noEmit && vite build",  // 先类型检查再打包
    "typecheck": "tsc --noEmit"             // 独立检查
  }
}
```

**为什么 dev 不检查**：

- 类型检查慢，影响 dev 启动与 HMR。
- esbuild 转译极快（10-100x 于 tsc）。
- 类型错误可在保存时由 IDE 显示，无需 dev 阻塞。

**为什么 build 要检查**：

- 防止类型错误的生产包。
- CI 卡 PR 类型错误。

**esbuild 配置**：

```ts
// vite.config.ts
export default {
  esbuild: {
    target: "es2022",
    legalComments: "none",
  },
  optimizeDeps: {
    esbuildOptions: { target: "es2022" },
  },
};
```

**vite-plugin-checker 在 dev 期显示类型错误**：

```ts
import checker from "vite-plugin-checker";
export default {
  plugins: [
    checker({
      typescript: true,  // 在 overlay 显示类型错误
      overlay: { initialIsOpen: false },
    }),
  ],
};
```

### 13. ts-node 与 tsx 怎么选？

**核心答案**：`tsx` 基于 esbuild，速度快、配置简单；`ts-node` 更老、配置复杂但兼容性好。

| 工具 | 速度 | 配置 | 兼容性 |
|---|---|---|---|
| `tsx` | 极快（esbuild） | 几乎零配置 | 现代 Node |
| `ts-node` | 慢 | tsconfig + transpileOnly | 老项目 |

**tsx 使用**：

```bash
pnpm add -D tsx
npx tsx script.ts           # 一次性
npx tsx watch script.ts     # 监听
```

```json
{
  "scripts": {
    "build:config": "tsx scripts/build.ts",
    "watch:scripts": "tsx watch scripts/build.ts"
  }
}
```

**ts-node 使用**：

```bash
pnpm add -D ts-node
npx ts-node script.ts
```

```json
// tsconfig.json
{
  "ts-node": {
    "transpileOnly": true,   // 跳过类型检查提速
    "compilerOptions": {
      "module": "CommonJS"
    }
  }
}
```

**选型**：

- 新项目用 `tsx`（快、简单）。
- 老项目或需 `ts-node` 特定能力（如 REPL）才用 ts-node。

## 六、Project References 类（高频）

### 14. Project References 解决什么问题？怎么用？

**核心答案**：解决 Monorepo 多包全量 tsc 慢、依赖关系不清的问题。每个包独立 tsconfig，tsc 增量编译。

**痛点**：

- Monorepo 多个 TS 包，全量 `tsc` 编译慢。
- 包间依赖关系不清晰，类型检查全项目串行。
- 改一个包要重编译所有包。

**配置**：

```json
// 根 tsconfig.json
{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/ui" },
    { "path": "./packages/web" }
  ]
}
```

```json
// packages/shared/tsconfig.json
{
  "compilerOptions": {
    "composite": true,        // 必须开启
    "declaration": true,      // 生成 .d.ts
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

```json
// packages/ui/tsconfig.json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "composite": true,
    "outDir": "dist"
  },
  "references": [
    { "path": "../shared" }    // 引用 shared 包
  ],
  "include": ["src"]
}
```

**增量编译**：

```bash
# 只编译变动的包及下游
tsc --build

# 强制全量
tsc --build --force

# 监听
tsc --build --watch
```

**关键选项**：

- `composite: true`：开启 project reference 支持。
- `declaration: true`：生成 `.d.ts` 让其他包 import。
- `declarationMap: true`：生成 `.d.ts.map`，IDE 跳转回源码。
- `outDir`：每个包独立输出目录。

## 七、性能与陷阱类（高频）

### 15. TS 编译慢怎么优化？常见陷阱有哪些？

**核心答案**：用增量编译、skipLibCheck、类型检查与转译分离、避免大 union 等手段。

**优化手段**：

```json
// tsconfig.json
{
  "compilerOptions": {
    "skipLibCheck": true,                              // 跳过 .d.ts 检查
    "incremental": true,                               // 增量编译
    "composite": true,                                  // 配合 project references
    "assumeChangesOnlyAffectDirectDependencies": true  // 假设改动只影响直接依赖
  }
}
```

```bash
# 增量编译
tsc --noEmit --incremental --tsBuildInfoFile .tsbuildinfo

# 项目引用
tsc --build
```

**类型检查与转译分离**：

```json
{
  "scripts": {
    "dev": "vite",                  // 只转译
    "build": "tsc --noEmit && vite build",
    "typecheck": "tsc --noEmit"
  }
}
```

**类型导入优化**：

```ts
import type { User } from "./types";  // 让打包器擦除
import { getUser } from "./api";
```

```json
"verbatimModuleSyntax": true
```

**避免大 union**：

```ts
// 慢：上千个字面量
type Route = "/a" | "/b" | /* 1000 个 */;

// 快：用模板字面量
type Route = `/${string}`;
```

**常见陷阱**：

1. **Cannot use import statement outside a module**：tsconfig module 与 package.json type 不一致。
2. **Property 'X' does not exist on type 'Window'**：未声明扩展。
3. **类型导入在运行时残留**：未用 `import type`。
4. **const enum 在 isolatedModules 报错**：用字面量 union 替代。
5. **'React' must be in scope**：jsx 配置错，React 17+ 用 `react-jsx`。

## 八、生产最佳实践

### 8.1 推荐 tsconfig.json（Vite + React 项目）

## 九、最佳实践 Checklist

### 9.1 配置

- `target` 与项目环境一致（ES2022 现代项目）
- `module` + `moduleResolution` 与运行环境一致
- `lib` 包含所需 API（DOM for browser, @types/node for Node）
- `jsx: "react-jsx"`（React 17+）
- `strict: true`
- `esModuleInterop: true`
- `skipLibCheck: true`
- `isolatedModules: true`（Vite/esbuild 必开）
- `noEmit: true`（配合打包器）
- `paths` 与 Vite/Webpack alias 同步
- `verbatimModuleSyntax: true`（强制类型导入）

### 9.2 类型声明

- `src/vite-env.d.ts` 声明环境变量与资源
- 第三方无类型包用 `declare module`
- `globals.d.ts` 扩展 window/globalThis
- 发布库时生成 `.d.ts`（vite-plugin-dts）

### 9.3 类型与运行时

- 类型导入用 `import type`
- 不依赖运行时类型信息
- enum 谨慎用（考虑字面量 union）
- 类型断言 `as` 不滥用

### 9.4 工程化

- dev 只转译不检查（Vite + esbuild）
- CI 跑 `tsc --noEmit` 类型检查
- `typecheck` 独立 scripts
- `vite-plugin-checker` 在 dev 显示类型错误

### 9.5 Monorepo

- 根 tsconfig 用 references
- 各包 `composite: true` + `declaration: true`
- `tsc --build` 增量编译
- 共享 `tsconfig.base.json` 继承

### 9.6 性能

- `skipLibCheck: true`
- `incremental: true` 或 `tsc --build`
- 类型导入用 `import type`
- 避免超大 union 类型
- 类型检查与转译分离

### 9.7 团队规范

- `strict: true` 全开
- 禁用 `any`（`@typescript-eslint/no-explicit-any`）
- 函数必须有显式返回类型
- 公共 API 类型放 `types/` 集中管理

## 十、一句话总纲

> TypeScript 工程化的本质是 **"静态类型检查 + 编译时类型擦除"**：tsconfig 控制编译行为（target/module/strict/lib/jsx）；类型声明 `.d.ts` 让无类型包也能类型安全；类型与运行时分离——类型只在编译时存在、enum 例外；类型检查与转译分离——Vite/Webpack 用 esbuild/SWC 快速转译、CI 跑 `tsc --noEmit` 类型检查；isolatedModules 让 esbuild 独立编译可行、强制类型导入用 `import type`；Project References 让 Monorepo 增量编译。能答出"TS 与 JS 关系""tsconfig 各字段作用""类型检查与编译为何分离""类型与运行时的差异""isolatedModules 解决什么""Project References 怎么用""怎么发库的类型"，就是高级前端对 TS 工程化的认知。
