# Go 互斥锁（Mutex）：悲观锁

> **sync.Mutex 是悲观锁**：每次访问共享资源前都先加锁，强制其他访问者等待，无论是否真会发生冲突。核心目标是保证同一时间只有一个 Goroutine 执行临界区代码。

---

## 一、互斥锁是什么

`sync.Mutex`（互斥锁）是用于保证共享资源在并发环境下**安全访问**的同步机制。它通过**独占访问**的方式，确保**同一时间只有一个 Goroutine** 能执行临界区代码（即被锁保护的代码段），从而避免多个 Goroutine 同时操作共享资源导致的数据竞争和不一致问题。

```go
var mu sync.Mutex
var count int

mu.Lock()        // 加锁
count++          // 临界区
mu.Unlock()      // 解锁
```

---

## 二、为什么互斥锁是悲观锁

**互斥锁（sync.Mutex）属于悲观锁**，原因如下：

- **悲观锁的核心思想**：假设并发访问共享资源时一定会发生冲突（即"悲观"地认为冲突是常态），因此在每次访问资源前，都会**先加锁**，强制其他访问者等待，直到当前操作完成并释放锁；
- **Mutex 的行为符合悲观锁定义**：
  - 每次访问共享资源前，必须先通过 `Lock()` 获取锁，**无论是否真的会发生冲突**；
  - 即使实际冲突概率很低，也会**严格限制并发访问**，通过阻塞等待保证安全性。

---

## 三、与乐观锁的对比

乐观锁的思想与悲观锁相反：

- **假设并发访问时冲突很少发生**，因此不主动加锁，而是在**操作结束时检查是否有冲突**（通常通过版本号或 CAS 操作实现）；
- 若没有冲突，则操作成功；若有冲突，则重试或报错。

| 维度 | 悲观锁（Mutex） | 乐观锁（CAS/版本号） |
|------|----------------|----------------------|
| 前提假设 | 冲突是常态 | 冲突很少 |
| 加锁时机 | **访问前** | **提交时检查** |
| 冲突处理 | 阻塞等待 | 重试或报错 |
| 适用场景 | 写多、竞争激烈 | 读多、冲突少 |

---

## 四、高频自测

1. Mutex 是悲观锁还是乐观锁？
   → **悲观锁**（每次访问前先加锁，假设必冲突）。
2. 乐观锁的两种常见实现？
   → **版本号、CAS 操作**。
3. 什么时候用乐观锁？
   → **冲突很少（读多写少）** 的场景，避免加锁开销。

---

## 五、一句话总结

> **Mutex = 悲观锁：假设必冲突，访问前先 Lock、用完 Unlock，独占临界区**。乐观锁则相反——不锁访问、提交时用版本号/CAS 校验，冲突才重试。
