# Go 并发模式：Pipeline / Worker Pool / Fan-out·Fan-in

本目录用三个小 demo 演示常见的 **goroutine + channel** 用法，对应源码：

| 模式 | 入口函数 | 源文件 |
|------|----------|--------|
| 流水线 | `pipeline()` | `pipeline.go` |
| 工作池 | `workerPool()` | `workerpool.go` |
| 扇出 / 扇入 | `fanOutIn()` | `fan-out-in.go` |

在 `main.go` 中切换要运行的 demo（取消注释对应调用即可）。

---

## 1. Pipeline（流水线）

### 做什么

把处理拆成若干 **串行阶段**，阶段之间只用 channel 连接：上游产出 → 下游消费，类似工厂流水线。

```
generate → square → output
```

### 主要场景

- 固定、可拆分的 **流式 / ETL**：读日志 → 解析 → 过滤 → 落库
- 每个阶段职责不同，但 **一条数据只沿一条链往前走**
- 希望阶段 **解耦**（改某一阶段的实现，只要保持 channel 契约即可）

### 优势

- 结构清晰，和 Unix 管道一样直观
- 各阶段可 **并行重叠**：上游还在生成，下游已在处理（背压由 channel 自然形成）
- 易扩展：中间插入 `filter(in) <-chan` 等阶段即可

### 局限

- 多为 **单链**；某一阶段 CPU 过重时，容易成为整条链的瓶颈
- 无缓冲 channel 时，慢阶段会阻塞上游（有时这正是需要的同步方式）

---

## 2. Worker Pool（工作池）

### 做什么

**一个任务队列** + **固定数量 worker** 从队列取任务；主 goroutine 投递任务、`close(jobs)`，再按任务数量收集结果。

```
        ┌→ worker ─┐
jobs ───┼→ worker ─┼→ results → processResult
        └→ worker ─┘
```

### 主要场景

- **大量同类、可并行** 的任务：HTTP 抓取、缩略图、批量 RPC、分片写库
- 需要 **限制并发度**（避免为每个任务起一个 goroutine）
- 任务 **彼此独立**，完成顺序通常不重要

### 优势

- **并发可控**：`numWorkers` 即上限，资源占用可预期
- **负载均衡**：空闲 worker 从 `jobs` 取下一个任务
- 心智模型接近「线程池」，适合 **同质任务**

### 局限

- 不适合用单一队列表达「每个任务要经过多段不同流水线」的完整业务（常需与 pipeline 组合）
- 结果 **默认乱序**；若要按 Job ID 有序，需自行排序或按序收集
- 生产环境还需考虑：错误传递、超时、`WaitGroup`、是否 `close(results)` 等（demo 做了最简版）

### 与 Pipeline 的区别（一句话）

- **Pipeline**：强调 **阶段分工**、数据沿链传递  
- **Worker Pool**：强调 **同类任务并行** + **限流**

## 3. Fan-out / Fan-in（扇出 / 扇入）

### 做什么

- **Fan-out**：一路输入 **分发** 到多路。本 demo 为 **广播**：每个值依次写入 `out1`、`out2`（两路各一份）
- **Fan-in**：多路输入通过 `select` **合并** 为一路；某路 `close` 后将对应 channel 置为 `nil`，两路都结束后 `close(out)`

```
        ┌→ square ──┐
input ──┤ fanOut    ├─ fanIn → 合并输出
        └→ double ──┘
```

### 主要场景

- **同一份数据多种处理**：一路算指标、一路写缓存、一路发通知（广播）
- **多源汇总**：多个生产者 / 多个分片的结果合并成一条流
- **并行加速**：也可将 fan-out 理解为多个 **相同** worker 共读一个 channel（每个值只被一个 worker 处理），再 fan-in 收集——与 Worker Pool 思路接近

### 优势

- **拓扑灵活**：分叉、汇合，不限于单链
- Fan-in 中对已关闭 channel 赋 `nil`，是 Go 里常见的 **多路合并** 写法
- 适合多路 I/O、多生产者汇总

### 局限

- 广播时 **每路都必须有消费者**，否则可能在 `fanOut` 写某一路时阻塞（无缓冲 channel 更明显）
- 合并后 **顺序不确定**；本 demo 对每个 `i` 会产出 `i²` 与 `2i` 两条结果，打印顺序可能交错
- 拓扑复杂时，`close` 时机与 goroutine 生命周期更容易出错，需仔细设计

### 与 Worker Pool 的区别

| | Worker Pool（本目录 demo） | Fan-out 广播（本目录 demo） |
|--|---------------------------|------------------------------|
| 任务如何处理 | 每个任务 **只被一个** worker 处理 | 每个值 **复制到多路**，可走不同逻辑 |
| 典型意图 | 限并发、抢队列 | 一分多、或多源合一 |

---

## 三者对照

| 维度 | Pipeline | Worker Pool | Fan-out / Fan-in |
|------|----------|-------------|------------------|
| 核心问题 | 分阶段串联 | 限并发处理同类任务 | 分叉或汇合数据流 |
| 数据路径 | 单链 | 每任务处理一次 | 可广播或多源合并 |
| 并行方式 | 阶段间流水线重叠 | 多 worker 抢任务 | 多路并行或多读 |
| 顺序 | 链上相对直观 | 结果常乱序 | 合并后常乱序 |
| 更适合 | 流式、多步骤转换 | 批量独立任务 | 多路处理 / 多源汇总 |

---

## 实际选型参考

- **消息流：解析 →  enrich → 存储**：优先 **Pipeline**；落库前若需批量写，最后一段可再接 **Worker Pool**
- **上万张图片生成缩略图**：**Worker Pool**（例如固定 8～16 个 worker）
- **同一业务既要风控又要审计又要推送**：**Fan-out** 多路，各路可再接自己的 pipeline；汇总监控可用 **Fan-in**

三个 demo 用整数做平方/加倍，是为了看清 channel 行为；换成网络请求、文件分块、消息包，模式相同。
