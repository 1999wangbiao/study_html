# 访问者模式（Visitor Pattern）— Go 语言

访问者模式的核心一句话：

> **把「数据结构」和「对数据的操作」拆开**——结构稳定时，新增操作不必改原有类型。

---

## 1. 定义

### 1.1 官方味道的定义

访问者模式是一种**行为型**设计模式：在**不修改**元素类的前提下，为对象结构中的元素定义**新的操作**。

做法是：

1. 元素（Element）提供一个 `Accept(visitor)`，把自己交给访问者。
2. 访问者（Visitor）为**每一种**元素类型提供一个 `VisitXxx` 方法。
3. 调用方遍历对象结构，对每个元素调用 `Accept`，真正干活的逻辑在 Visitor 里。

### 1.2 双重分派（Double Dispatch）在说什么

普通方法调用是「一次分派」：运行时只按**接收者类型**选实现。

访问者模式是「两次分派」：

1. 第一次：`element.Accept(v)` —— 按**元素真实类型**进到对应 `Accept`。
2. 第二次：`v.VisitConcreteA(a)` —— 按**访问者类型 + 元素类型**选到具体操作。

Go 没有方法重载，所以常用写法是：每种元素在 `Accept` 里**显式调用** Visitor 上对应的方法，从而模拟双重分派。

```text
Client
  │
  │  Accept(visitor)
  ▼
Element (接口) ──Accept──► ConcreteElementA / B
                              │
                              │ visitor.VisitA(this) / VisitB(this)
                              ▼
                         Visitor (接口)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
            ConcreteVisitor1    ConcreteVisitor2
            （计价）              （导出 XML）
```

### 1.3 和「直接在类型上加方法」的对比

| 做法 | 优点 | 缺点 |
|------|------|------|
| 在元素上不断加方法 | 调用直观 | 每加一种操作都改所有元素类 |
| 访问者把操作外置 | 新操作 = 新 Visitor，元素类少动 | 新元素类型时，所有 Visitor 都要改 |

记忆口诀：

- **元素稳定、操作常变** → 适合访问者。
- **操作稳定、元素常变** → 更适合普通接口 / 策略，而不是访问者。

---

## 2. 常见场景

| 场景 | 为什么适合 |
|------|------------|
| 编译器 / AST | 语法树节点种类相对固定；类型检查、求值、打印、优化是多种「路过」操作 |
| 文档 / 报表对象结构 | 段落、表格、图片固定；导出 PDF、统计字数、校验是多种操作 |
| 图形编辑器场景图 | Shape 种类有限；渲染、碰撞检测、序列化分开实现 |
| 规则引擎 / 计费 | 商品、优惠券、运费等元素结构稳定；计价、审计、埋点各写一个 Visitor |
| 跨类型统一遍历 | 需要「走过整棵对象树，对不同节点做不同事」，又不想把逻辑塞进节点本身 |

Go 里更接地气的说法：

- 一堆 `interface` 实现类型已经定型。
- 业务上还要反复「对这棵结构做第 N 种处理」。
- 又不想把计费、导出、校验全堆进每个 `struct` 的方法里。

此时 Visitor 把「操作」收成独立类型，职责更清晰。

## 3. 示范代码

下面用「电商订单元素 + 两种操作（计价 / 导出描述）」说明。元素类型稳定：商品行、优惠券、运费；操作会增长。

### 3.1 元素与访问者接口

```go
package main

import (
	"fmt"
	"strings"
)

// OrderVisitor：对订单里每一种元素的操作集合。
// 新增一种「操作」（如审计）= 新增一个实现此接口的类型。
type OrderVisitor interface {
	VisitProduct(p *Product)
	VisitCoupon(c *Coupon)
	VisitShipping(s *Shipping)
}

// OrderElement：可被访问的订单元素。
type OrderElement interface {
	Accept(v OrderVisitor)
}
```

### 3.2 具体元素：Accept 里完成第二次分派

```go
// Product：商品行。
type Product struct {
	Name  string
	Price float64
	Qty   int
}

func (p *Product) Accept(v OrderVisitor) {
	v.VisitProduct(p) // 双重分派的第二步：告诉 Visitor「我是 Product」
}

// Coupon：优惠券（满减简化为固定减免）。
type Coupon struct {
	Code   string
	Amount float64
}

func (c *Coupon) Accept(v OrderVisitor) {
	v.VisitCoupon(c)
}

// Shipping：运费。
type Shipping struct {
	Carrier string
	Fee     float64
}

func (s *Shipping) Accept(v OrderVisitor) {
	v.VisitShipping(s)
}
```

### 3.3 对象结构：订单 = 元素列表

```go
// Order：稳定的对象结构，只负责持有元素并接受 Visitor 遍历。
type Order struct {
	Items []OrderElement
}

func (o *Order) Accept(v OrderVisitor) {
	for _, item := range o.Items {
		item.Accept(v)
	}
}
```

### 3.4 具体访问者 1：计价

```go
// PricingVisitor：计算应付金额（操作 A）。
type PricingVisitor struct {
	Total float64
}

func (v *PricingVisitor) VisitProduct(p *Product) {
	v.Total += p.Price * float64(p.Qty)
}

func (v *PricingVisitor) VisitCoupon(c *Coupon) {
	v.Total -= c.Amount
	if v.Total < 0 {
		v.Total = 0
	}
}

func (v *PricingVisitor) VisitShipping(s *Shipping) {
	v.Total += s.Fee
}
```

### 3.5 具体访问者 2：导出可读描述

```go
// DescribeVisitor：导出人类可读摘要（操作 B，不改任何元素类型）。
type DescribeVisitor struct {
	Lines []string
}

func (v *DescribeVisitor) VisitProduct(p *Product) {
	v.Lines = append(v.Lines,
		fmt.Sprintf("商品 %s x%d = %.2f", p.Name, p.Qty, p.Price*float64(p.Qty)))
}

func (v *DescribeVisitor) VisitCoupon(c *Coupon) {
	v.Lines = append(v.Lines,
		fmt.Sprintf("优惠券 %s -%.2f", c.Code, c.Amount))
}

func (v *DescribeVisitor) VisitShipping(s *Shipping) {
	v.Lines = append(v.Lines,
		fmt.Sprintf("运费(%s) +%.2f", s.Carrier, s.Fee))
}

func (v *DescribeVisitor) String() string {
	return strings.Join(v.Lines, "\n")
}
```

### 3.6 使用方式

```go
func main() {
	order := &Order{
		Items: []OrderElement{
			&Product{Name: "键盘", Price: 299, Qty: 1},
			&Product{Name: "鼠标", Price: 99, Qty: 2},
			&Coupon{Code: "SAVE50", Amount: 50},
			&Shipping{Carrier: "SF", Fee: 12},
		},
	}

	pricing := &PricingVisitor{}
	order.Accept(pricing)
	fmt.Printf("应付: %.2f\n", pricing.Total)

	desc := &DescribeVisitor{}
	order.Accept(desc)
	fmt.Println("--- 明细 ---")
	fmt.Println(desc.String())
}
```

示例输出：

```text
应付: 459.00
--- 明细 ---
商品 键盘 x1 = 299.00
商品 鼠标 x2 = 198.00
优惠券 SAVE50 -50.00
运费(SF) +12.00
```

### 3.7 调用链拆解（对照双重分派）

```text
order.Accept(pricing)
  → product.Accept(pricing)   // 分派 1：进到 *Product.Accept
      → pricing.VisitProduct  // 分派 2：进到计价逻辑
  → coupon.Accept(pricing)
      → pricing.VisitCoupon
  → ...
```

同一条 `order.Accept(desc)` 路径不变，只是第二次分派落到 `DescribeVisitor` 的各个 `Visit*`。

### 3.8 Go 里的注意点

1. **接口方法要齐**：`OrderVisitor` 为每种元素留一个方法；新增元素类型时，所有 Visitor 实现都要补方法（编译器会逼你改，这是刻意的）。
2. **用指针还是值**：示例里元素用指针接收者，避免拷贝，也方便 Visitor 需要时改状态（本例只读）。
3. **不要和 `type switch` 混为一谈**：在一个函数里对 `interface{}` 做 `switch x.(type)` 也能「按类型办事」，但操作一多就会变成巨大的 switch；Visitor 把每种操作收成独立类型，扩展操作时更干净。
4. **Go 惯用替代**：若元素种类会频繁增加，团队更常直接用小接口 + 策略函数，而不是经典 Visitor；经典 Visitor 更适合「元素集合封闭、算法集合开放」。

---

## 4. 总结

### 4.1 记住三件事

1. **意图**：操作与结构分离；新操作主要通过新 Visitor 扩展。
2. **机制**：`Accept` + `VisitXxx` 模拟双重分派，让「正确的元素」遇到「正确的操作」。
3. **适用边界**：元素稳定、操作多变时香；反过来则痛苦（每加一种元素就改遍所有 Visitor）。

### 4.2 优缺点速查

| | 说明 |
|---|------|
| 优点 | 新增操作不改元素类；相关操作集中在一个 Visitor 里，好读也好测 |
| 优点 | 遍历与算法解耦，同一结构可套用多种 Visitor |
| 缺点 | 新增元素类型成本高，破坏「对修改关闭」的另一面 |
| 缺点 | 元素要暴露足够信息给 Visitor，可能削弱封装 |
| 缺点 | 类 / 接口数量变多，简单场景容易过度设计 |

### 4.3 选型一句话

> 对象结构像一棵「不怎么长新节点种类」的树，但你经常要对它做第 N 种处理时，用访问者；若节点种类天天加，别用访问者，改用接口方法或策略。
