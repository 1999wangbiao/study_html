### 1. 内容站为优化流量，把所有图片都加了loading="lazy"。上线后非首屏流量下降，但首页LCP变差，因为首屏主图也被延迟加载。更合理的图片策略是什么？（2分）

**A.** 删除首屏主图，用纯色背景替代，LCP就不会受图片影响。

**B.** 所有图片继续lazy，只要网络请求少，总体性能一定更好，并在弱网、重复操作和异常路径下复测

**C.** 首屏关键图保持高优先级加载，非首屏图片使用懒加载和合理占位。

**D.** 将首屏主图转成base64，其他图片保持原样。

**正确答案：** C　|　**我的答案：** C　|　✅

**答案详解：** 核心考点：懒加载要"分屏而治"——首屏关键资源不能被 lazy 拖慢。结合场景：全站图片 loading="lazy" 后，首屏主图被延迟加载，导致首屏流量下降但首页 LCP 变差。C ✅：首屏关键图（LCP 元素）保持高优先级即时加载（如 fetchpriority="high"），非首屏图片才用懒加载并配合理占位，兼顾流量与首屏性能。A ❌：删除首屏主图直接损失内容价值与视觉表达，不是优化图片策略。B ❌：无脑全懒加载在省请求的同时牺牲了首屏关键图渲染时机，总体性能不一定更好，且应在弱网等路径下复测也不成立。D ❌：转 base64 会内联进文档/JS 增大体积，首屏主图为大图时反而更差。

### 2. 主站通过iframe嵌入第三方客服页面。客服页使用postMessage通知主站打开用户资料。当前主站没有校验origin，只要收到{type:"openUser"}就执行。最关键的修复是什么？（2分）

**A.** 只在HTTPS页面使用postMessage，HTTPS会自动验证消息来源。

**B.** 将消息内容改成Base64编码，避免普通用户看懂数据。

**C.** 把iframe设置为display:none，减少被攻击者操作的机会。

**D.** 校验event.origin和消息结构，只接受可信来源和白名单动作。

**正确答案：** D　|　**我的答案：** D　|　✅

**答案详解：** 核心考点：postMessage 必须校验来源（origin）与消息结构白名单。结合场景：主站收到 {type:"openUser"} 就执行，任何恶意 iframe/第三方页面都能伪造消息触发打开用户资料。D ✅：校验 event.origin 是否属于可信白名单，并校验消息结构与动作白名单，只接受可信来源的合法动作，是最关键的修复。A ❌：HTTPS 只保证传输加密，不会自动验证消息来源。B ❌：Base64 只是编码不是安全措施，任何人都能解码。C ❌：display:none 只隐藏页面显示，攻击者仍可操作 iframe 向主站 postMessage。

### 3. 移动端表单填写较长，用户在地铁弱网中经常提交失败。产品希望用户输入不丢失，并在网络恢复后可继续提交。表单包含备注、图片和地址选择。更合理的前端方案是什么？（2分）

**C.** 只在用户点击返回时弹窗确认，提交失败不做额外处理。

**D.** 提交失败后清空表单，要求用户重新填写，避免提交旧数据。

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点：弱网场景下的数据不丢失方案（本地草稿+上传状态+网络感知）。结合场景：地铁弱网、长表单、含备注/图片/地址选择，提交经常失败。A ✅：本地保存草稿与上传状态，监听网络变化，网络恢复后提示用户继续提交或重试，既保数据又不丢体验，是最合理的方案。B ❌：每次输入都立即请求服务端，弱网下请求更多、失败率更高，还浪费流量、可能提交中间态。C ❌：只在返回时弹窗确认、提交失败不做处理，会直接丢数据。D ❌：提交失败清空表单要求重填，完全违背"输入不丢失"的核心诉求。

**答案详解：** 核心考点：Markdown→HTML 渲染的 XSS 深度防护。结合场景：marked 转 HTML 后再过滤 <script>，安全测试未直接弹窗，但未过滤事件属性、javascript: 协议、data: URL 等绕过路径。B ✅：用成熟 HTML sanitizer（如 DOMPurify）配白名单策略限制标签、属性与 URL 协议，并叠加 CSP 兜底，是上线前最关键的容忍面要求。A ❌：只开放登录用户并不能阻止"登录用户之间互相攻击"，且认证本身也可能被绕过。C ❌：把评论 HTML 存 localStorage 与恶意内容是否在前端执行、服务端是否存储无关。D ❌：只过滤 <script> 和 <iframe> 覆盖不全，`<img onerror>`、`<a href="javascript:">` 等同样能执行脚本。

### 5. 用户在一个标签页点击退出登录，另一个标签页仍停留在用户资料页，并能看到缓存的敏感信息。接口再次请求会401，但页面不主动跳转。最合适的前端补强是什么？（2分）

**A.** 只在用户刷新其他标签页时检查登录态，避免打断用户当前阅读。

**B.** 把token从localStorage改成sessionStorage，所有同步问题都会消失，同时补充线上监控和用户反馈观察

**C.** 退出时只清理当前标签页状态，其他标签页等接口失败后自然处理。

**D.** 使用`BroadcastChannel`或`storage`事件同步退出事件，其他标签页清理状态并跳转。

**正确答案：** D　|　**我的答案：** D　|　✅

**答案详解：** 核心考点：多标签页的登录态同步（跨标签通信）。结合场景：一个标签页退出登录，另一个标签页仍停在使用户资料页并缓存敏感信息，接口 401 后也不跳转。D ✅：用 BroadcastChannel（同源多标签）或 storage 事件广播退出事件，其他标签页收到后清理状态并跳转登录，是最合适的前端补强。A ❌：只在用户刷新时才检查登录态，敏感信息在刷新前仍可见，且不满足"退出即生效"。B ❌：sessionStorage 按标签页隔离，改成它只是换了存储载体，并不会同步退出状态，"所有同步问题都会消失"不成立，还引入新限制。C ❌：退出时只清理当前标签页、其他等接口失败自然处理，会让其他页长时间展示已失效数据。

### 6. 公司接入SSO后，用户从认证域跳回业务域，偶尔没有登录态。排查发现Cookie在某些浏览器中没有带上。系统使用HTTPS，认证和业务在不同子域。最应该共同确认的配置是什么？（2分）

**A.** Cookie的`Domain`、`Secure`、`SameSite`、回跳域名和跨站跳转方式是否匹配。

**B.** 前端是否把登录态同时写入localStorage，作为Cookie失败时的备用方案，并在弱网、重复操作和异常路径下复测

**C.** 回跳页面是否等待3秒再请求用户信息，给浏览器更多时间写入Cookie。

**D.** 登录按钮是否使用`<button>`，避免表单默认提交被浏览器拦截。

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点：跨子域 SSO 回跳时 Cookie 携带问题的配置面。结合场景：认证与业务在不同子域，HTTPS 下部分浏览器不携带登录 Cookie。A ✅：应共同确认 Cookie 的 Domain（是否覆盖业务域）、Secure、SameSite，以及回跳域名与跨站跳转方式（302 重定向 vs fetch 跨域）是否互相匹配，这直接决定浏览器是否带上 Cookie。B ❌：把登录态写入 localStorage 只是旁路，解决不了"Cookie 不带"的根因，还引入 XSS 窃取 token 的新风险。C ❌：等待 3 秒不改变 Cookie 的携带条件，属无效等待。D ❌：登录按钮是否用 <button> 与 Cookie 携带、SSO 回跳无关。
