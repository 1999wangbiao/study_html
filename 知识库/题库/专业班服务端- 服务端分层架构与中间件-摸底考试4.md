### 1. 以下哪个命令用于在Docker中停止一个正在运行的容器?（5分）

**A.** docker stop

**B.** docker pause

**C.** docker end

**D.** docker halt

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是 Docker 容器的生命周期管理。A ✅ `docker stop` 会发送 SIGTERM 信号优雅停止容器，超时后再强制 SIGKILL，是停止运行中容器的标准命令；B ❌ `docker pause` 只是将容器内所有进程挂起（冻结），容器仍处于运行态，可随时 unpause 恢复；C ❌ Docker 不存在 `docker end` 子命令；D ❌ Docker 也不存在 `docker halt` 子命令，停止容器只有 stop（及 kill）。

### 7. 下列代码的输出结果是什么？（5分）

> ```go
> package main
> 
> import (
> 	"fmt"
> 	"sync"
> )
> 
> func main() {
> 	var wg sync.WaitGroup
> 	for i := 0; i < 3; i++ {
> 		wg.Add(1)
> 		go func(i int) {
> 			defer wg.Done()
> 			fmt.Println(i)
> 		}(i)
> 	}
> 	wg.Wait()
> }
> 
> ```

**A.** 打印 0 1 2，顺序不定

**B.** 打印三次 2

**C.** 编译错误

**D.** 打印顺序一定是 0 1 2

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是 Go 并发中 goroutine 的调度特性。A ✅ 本题为并发打印代码：每次迭代启动一个 goroutine 分别打印循环变量 0、1、2（若循环变量以参数副本传入，或使用 Go 1.22+ 每轮迭代独立的循环变量），三个 goroutine 由 Go 运行时调度，先后次序无法保证，所以会“打印 0 1 2，但顺序不定”；B ❌ “打印三次 2”是旧版 Go 中闭包直接引用循环变量、未传入副本时的典型错误结果，与正确代码的行为不符；C ❌ 该代码是合法的，不会产生编译错误；D ❌ goroutine 并发调度没有先后保证，不可能“一定”按 0 1 2 顺序输出。解答本题的关键是理解 goroutine 的调度由运行时决定、不保证顺序。

### 8. 下列哪个WHERE子句中的条件最有可能导致create_time字段上的索引失效？（5分）

**A.** WHERE YEAR(create_time) = 2023

**B.** WHERE create_time >= '2023-01-01' AND create_time < '2023-02-01'

**C.** WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'

**D.** WHERE create_time = '2023-06-01'

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是对索引列使用函数导致索引失效。A ✅ WHERE 中对索引列 create_time 套用 `YEAR()` 函数后，MySQL 无法按索引树的有序值直接比较，必须对每一行先计算函数结果再过滤，索引失效，所以 A 最可能破坏索引使用；B ❌ create_time 直接与常量进行区间比较，索引可以正常做范围扫描；C ❌ `BETWEEN ... AND ...` 本质仍是 create_time 直接参与的范围比较，同样可以走索引；D ❌ 等值匹配 `=` 直接用列本身参与比较，是最利于使用索引的形式。规律可记：尽量让索引列裸身参与比较，别在列上套函数。

### 9. 在大数据表进行LIMIT深分页时，下列哪种SQL写法具有优化作用？（5分）

**A.** SELECT * FROM table WHERE id > (SELECT id FROM table ORDER BY id LIMIT 100000, 1) LIMIT 10

**B.** SELECT * FROM table LIMIT 100000, 10

**C.** SELECT * FROM table WHERE name LIKE '%abc%' LIMIT 10

**D.** SELECT * FROM table ORDER BY RAND() LIMIT 10

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是深分页（延迟关联/主键筛选）优化。A ✅ 该写法先在子查询里利用索引 `ORDER BY id LIMIT 100000, 1` 快速定位偏移位置对应的主键 id，外层再按主键查出 10 条数据，无需把前面 10 万行全部读出来再丢弃，扫描行数大幅减少，因此有优化作用；B ❌ `LIMIT 100000, 10` 正是最朴素的深分页写法，MySQL 必须扫描并跳过前面 10 万行，IO 开销巨大；C ❌ 前导通配符 `LIKE '%abc%'` 无法利用索引，本身就是低效查询，与深分页优化无关；D ❌ `ORDER BY RAND()` 需要对全表生成随机值并排序，代价极高，绝不推荐。

### 10. 在优化MySQL的深分页查询（如 LIMIT 100000, 10）时，推荐使用哪种技术以显著减少扫描的行数？（5分）

**A.** 基于索引的子查询配合主键筛选

**B.** 添加更多字段到SELECT查询列表

**C.** 在ORDER BY后对LIMIT增加OFFSET参数

**D.** 增加连接数以提升并发执行

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是深分页优化的核心思路——用索引减少扫描行数。A ✅ 基于索引的子查询配合主键筛选（即“延迟关联/lazy offset”），先在索引上定位第 100000 行之后对应的主键，再用主键回表取数据，能把需要扫描的行数从 10 万级降到几十行，是官方推荐的深分页优化方案；B ❌ 往 SELECT 列表里加更多字段与扫描行数无关，反而可能增加回表、增大 IO；C ❌ OFFSET 正是深分页开销的根源，继续加大 OFFSET 只会更慢；D ❌ 增加并发连接只影响整体吞吐能力，并不能减少单条查询的扫描行数。

### 14. 在Go服务的Dockerfile中，如何安排COPY指令和依赖安装指令顺序以最大程度利用缓存？（5分）

**A.** 先COPY go.mod和go.sum，再执行依赖安装，然后再COPY源码

**B.** 全部文件一次性COPY到镜像后，统一安装依赖

**C.** 先安装依赖，再COPY go.mod和go.sum

**D.** 先COPY源码，再COPY go.mod和go.sum，然后安装依赖

**正确答案：** A　|　**我的答案：** A　|　✅

**答案详解：** 核心考点是 Docker 构建缓存机制——只有指令及其输入（被 COPY 的文件）都没变化时，对应层缓存才会命中。A ✅ go.mod / go.sum（依赖清单）的变更频率远低于源码，先 COPY 它们执行依赖安装，之后每次只改源码时，前面的依赖层都能命中缓存，无需重新下载依赖，最大化复用缓存；B ❌ 一次性 COPY 全部文件，只要源码有改动，依赖层缓存就会连带失效，每次都要重新安装依赖；C ❌ 尚未 COPY 依赖清单就“先安装依赖”，逻辑上无法执行；D ❌ 先把源码 COPY 进来已使缓存失效，随后再 COPY go.mod 就失去了利用缓存的时机。

### 19. 哪种HTTP状态码代表“未修改”？（5分）

**A.** 200 OK

**B.** 304 Not Modified

**C.** 404 Not Found

**D.** 500 Internal Server Error

**正确答案：** B　|　**我的答案：** B　|　✅

**答案详解：** 核心考点是 Docker 构建缓存与镜像层优化。A ✅ 多阶段构建能去掉与运行无关的构建工具和中间产物，层数更少、镜像更小，整体构建与传输都更快；B ❌ 频繁更换基础镜像会使基础层缓存全部失效，每换一次都要重新拉取、重新构建底层，反而明显拖慢构建；C ✅ Docker 按“指令 + 上下文是否变化”分层缓存，充分利用已有层的缓存是加速构建的核心思路；D ✅ 把变更频率低的依赖声明/文件放在 Dockerfile 靠前位置，这样后续源码变动时，前面的依赖层缓存都能命中，不必重新安装依赖。故选 ACD。

**B.** 禁用所有外键以减少约束检查

### 5. 在Mysql中，针对慢查询优化有哪些有效方式？（5分）

**A.** 可以通过为查询字段建立合适的索引以减少全表扫描

**B.** 查询时尽量避免使用SELECT *，只查需要的字段有助于提升性能

**答案详解：** 核心考点是慢查询优化的有效方向。A ✅ 为 WHERE、JOIN、ORDER BY 涉及的字段建立合适的索引，能大幅减少全表扫描；B ✅ 尽量避免 SELECT *、只查询需要的列，可减少网络传输、内存占用与回表成本（配合覆盖索引收益更大）；C ❌ 增加表的数据量只会让扫描、排序变得更慢，与优化目标完全相悖；D ✅ 开启并分析慢查询日志，能准确定位执行时间长的低效 SQL，再结合 EXPLAIN 针对性优化，是系统化的优化流程。故选 ABD。

### 6. 在使用Docker时，如何实现数据的持久化存储?（5分）

**A.** 通过配置tmpfs挂载

**B.** 使用Docker Volume

**C.** 创建Bind Mounts

**D.** 在容器内部使用外部存储设备

**正确答案：** BC　|　**我的答案：** BC　|　✅

**答案详解：** 核心考点是 Docker 数据的持久化方案。B ✅ Docker Volume（命名卷）由 Docker 管理、存放于宿主机的卷目录中，数据与容器生命周期解耦，容器删除后数据仍在，是官方推荐的持久化方式；C ✅ Bind Mounts 把宿主机上的指定目录直接挂载进容器，两边共享同一份数据，同样可以实现持久化；A ❌ tmpfs 挂载的是内存中的临时文件系统，容器停止或重启后数据即丢失，不满足持久化要求；D ❌ 容器自身的可写层是临时的，随容器销毁而消失；仅“在容器内部使用外部存储设备”的说法含糊，未通过挂载/卷机制进行绑定就无法真正做到持久化。故选 BC。

**B.** 避免SELECT *，只获取必需的列

### 8. 关于MySQL数据库索引优化的考虑因素有哪些？（5分）

**A.** 考虑为那些经常作为查询条件的列添加索引

**B.** 为经常要排序、分组和联合操作的字段建立索引

**C.** 为经常更新的字段添加索引

**D.** 避免为表中的每个列都建立索引

**正确答案：** ABD　|　**我的答案：** ABD　|　✅

**答案详解：** 核心考点是索引设计的原则与取舍。A ✅ 经常作为查询条件（WHERE、JOIN 的 ON）的列建索引，往往能直接把全表扫描改为索引查找，收益最大；B ✅ 为经常排序（ORDER BY）、分组（GROUP BY）和联合操作（JOIN）涉及的字段建立索引，可借助索引的有序性避免文件排序、临时表，显著提速；C ❌ 频繁更新的字段上加索引，会让每次 INSERT/UPDATE 都要同步维护索引树，写放大明显，拖慢写入，通常不建议建；D ✅ 索引不是越多越好，为每列都建索引会占用大量磁盘、拖慢写入，还可能让优化器选出次优执行计划。故选 ABD。

**A.** 数据压缩率高，节省存储空间

**B.** 直接可读，无需反序列化
